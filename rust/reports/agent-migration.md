# Agent migration

## Phase 0: protocol source ownership

The ten authoritative protobuf files now live in
`crates/infrastructure/contracts/proto`. Their contents match the previously
accepted sources after CRLF-to-LF normalization. Package names, services, RPCs,
field numbers, enum values, presence and streaming shapes are unchanged.
`EDGE_AGENT_PROTOCOL_VERSION` remains 2. Both client and server bindings continue
to be generated by `citadel-contracts`.

The external-source manifest and its build-time checksum machinery were removed.
`contracts/tests/protocol_sources.rs` preserves the accepted source fingerprints
as a compatibility regression test. This baseline requires deliberate review
when changing the protocol; ordinary compilation only consumes Rust-owned files.

Docker API generation also depended on an external schema. The same schema is
now owned at `crates/infrastructure/docker-api/codegen/v1.49.yaml`, with LF line
endings and an updated source checksum. API and generator versions are unchanged.

The obsolete Phase 1 inventory generators were retired; their captured reports
remain historical evidence. The identity test script now runs its Rust checks
without invoking a separate runtime. Agent interoperability fixtures remain
available for compatibility testing and are not production build inputs.

CI checks out no submodules for Rust validation. It checks source ownership,
builds the Docker `rust-source` stage from a context containing only `rust/` and
`version.json`, then performs generation checks, workspace checks and tests.

Local isolation uses a private Linux mount namespace with an empty filesystem
over the external contracts directory. The developer checkout and running Core
are unaffected. Validation completed so far:

- `cargo check --locked --workspace` with the external directory hidden.
- Docker `rust-source` build from only `rust/` and `version.json`.
- Docker API regeneration with the external directory hidden: all 249 generated
  files match the committed output.
- Source-ownership check, including a negative fixture that it correctly rejects.

The isolated full workspace test run passed 711 tests and skipped 252 tests
requiring external fixtures. It exposed one pre-existing architecture failure:
volume-helper composition read `HOSTNAME` directly. That lookup now occurs in
startup configuration with the same empty-string fallback. The affected
`resource_structure` suite was rerun in isolation: all 10 tests passed.

Phase 0 is complete. The later Agent runtime and interoperability phases remain
pending; the skipped fixture tests do not establish their parity.

## Phase 1: executable, configuration and lifecycle

`crates/agent` now provides one `citadel-agent` executable, with separate app,
configuration and composition modules. It constructs the existing Docker client
without opening a database connection. The architecture gate permits the Agent
host while preventing features/infrastructure from depending on it, and prevents
Server and Agent from depending on each other.

Startup validates Direct public keys and TLS settings, Edge Core origins and
optional CA files, port bounds, Docker endpoints and all Swarm bootstrap identity
fields. Configuration tests consume the four deployment templates and cover all
five profiles. Enrollment tokens are not logged or included in Debug output.
Identity enrollment/file lifecycle belongs to Phase 4; configuration permits a
missing token so an enrolled Agent can reconnect using its persisted identity.

The unsigned `/health` endpoint provides process liveness. Direct mode binds all
IPv4 interfaces and supports configured TLS; Edge profiles bind loopback only.
Tracing reports the selected profile/listener without credential material.
Ctrl+C and SIGTERM initiate a bounded listener drain. Management RPCs and the
Edge connection remain unimplemented, and startup explicitly logs this scope.

At the end of Phase 1, only Unix Docker endpoints were usable; TCP/HTTP
composition was explicitly deferred. Phase 2 below adds that support without
fallback to a different daemon. Agent image packaging remains Phase 7.

All 12 Agent configuration/lifecycle tests pass, including real HTTP/HTTPS health,
mismatched/malformed TLS material, hostname verification, a real executable
receiving SIGTERM, and listener release. Tests require no database or Docker
daemon; TLS fixtures use OpenSSL and are removed after each test.

The 10 architecture checks and five Agent parity inventory checks also pass.
Strict Clippy for all Agent targets, formatting and source ownership checks pass.
Phase 1 is complete; the next implementation phase is shared Docker runtime parity.

## Phase 2: shared local Docker runtime

The Agent and Core share `DockerEndpoint` and `DockerClient` for Unix sockets and
explicit TCP/HTTP daemon addresses. Generated API calls, raw inspection, pull,
logs, events, statistics and upgraded exec connections use the selected endpoint.
Docker CLI build/stack execution uses the same address and clears inherited
context/TLS overrides. Unsupported endpoint schemes fail without a fallback.

Filtered list methods preserve container options and generated volume warnings;
Swarm task listing can include completed tasks. Pull/import options retain
source, repository, tag, changes and structured error codes. Docker version
results retain optional component metadata for BuildKit discovery.

Binary exec accepts generated execution options, preserves bytes and stream
identity, checks framing limits and inspects the exit status. Partial header and
payload reads are cancellable. Interactive execution accepts a command, supports
resize, drains output after input half-close and emits one inspected exit status.
Container/service logs and task snapshots share the bounded decoding transport.

Local runtime code no longer requires Core resource claims or database access:

- `DockerClient::apply_container_config` creates, starts and observes containers,
  including an ambiguous Start response and health-check state transitions.
- `external/stacks::LocalStackApply` stages source and credentials, runs
  Compose/Swarm with progress and cleans temporary files on completion, failure
  and token cancellation. Independent private directories avoid permission
  conflicts with staging directories left by another process user.
- `external/builds::runtime::DockerBuildSession` owns temporary credentials,
  registry login, build and push execution. Core retains Git materialization,
  secret resolution and target selection, then delegates local execution here.
  Transported archives are bounded and forwarded directly to Docker stdin;
  Citadel never extracts caller archives onto its own filesystem. Dockerfile
  paths, command arguments, secret redaction and process/output limits are
  checked at the shared runtime boundary.

Adapter integration fixtures cover selected-daemon routing, filters, pull/import,
log snapshots, binary framing and cancellation, interactive half-close and exit,
deployment observation, build credentials/redaction, and Compose/Swarm cleanup.
They need neither a database nor a Docker daemon and do not modify running Core.
The parity inventory distinguishes these reusable runtime additions from pending
wire mapping, authentication, restrictions and real-daemon interoperability.

Validation: 29 Docker transport tests, five local runtime tests, 151 adapter
unit tests, 12 Agent configuration/lifecycle tests, six contract tests and all
10 architecture checks pass. One adapter unit test remains ignored because it
requires an external fixture. Strict Clippy for all adapter/Agent/contracts
targets, formatting, whitespace and source ownership checks pass. The server
also builds as part of its architecture integration test.

Phase 2 is complete at the shared runtime boundary. Wire request preparation,
authentication and Direct/Edge interoperability remain the following phases.

## Phase 3: Direct Agent

The Agent now registers all eight gRPC services and 68 RPCs alongside unsigned
health on the HTTP/HTTPS listener. Every management route requires the established
Ed25519 signature, exact metadata lengths, timestamp skew and SHA-256 body hash.
An atomic, bounded nonce cache expires entries after timestamp + 60 seconds.
Authentication hashes the original first protobuf message rather than decoding
and reserializing its map fields; Core's existing signer and wire format are
unchanged. Duplex exec authenticates its Open message before starting Docker.

Handlers cover inventory, stats/events/log streams, interactive and binary exec,
image operations/builds, container deployment, Compose/Swarm apply, networks,
volumes and Swarm node/service/task/secret/config operations. Wire mappings preserve
optional false/zero values, integer versions, bytes, port modes and state names.
Swarm updates preserve unmanaged fields and forward registry authentication.

Streams use bounded queues and own their process/session cancellation. Build
credentials and stack staging are private and removed on failure, cancellation
or future drop. Identity-token registry credentials use private Docker config
and output redaction. Successful Compose secret mounts retain their files;
replacement cleanup only removes the preceding Agent-owned version. Swarm apply
has a five-minute bound, with Compose restoration after failed conversion.

Real Docker testing exposed terminal output loss on socket half-close. Interactive
sessions now signal terminal EOF while retaining the socket to drain output and
inspect the exit status. Binary stdout/stderr remain separate and preserve bytes.

Validation includes authentication coverage for all 68 routes, signed Core-client
map requests, TLS HTTP/2, deadline/replay/tamper/size rejection, representative
wire mutations, build cancellation/redaction and shared-runtime cleanup tests.
The live Docker fixture exercises Core platform info, inventory, statistics and
events plus container lifecycle, terminal/binary exec, logs, image inspection,
network/volume operations and deployment apply. It removes its own resources.

Validation results: 40 Agent unit/transport/configuration/lifecycle tests and the
opt-in Docker test pass. Shared-runtime checks pass: 151 adapter unit tests
(one external-fixture test ignored), 29 Docker transport tests, seven local-runtime
tests, six contract tests and 11 process/Git runner tests. Core compiles and its
10 architecture checks pass. Strict Clippy for Agent, adapters, contracts and
processes (all targets), formatting, whitespace and source ownership pass.

The Direct implementation is in place. It does not yet certify full interoperability
or production cutover: live Swarm-cluster mutations, external registry push and mixed-version
Agent binary interoperability remain compatibility gates. Edge connection and
command enforcement are the following phases.

## Phase 4: Edge identity and connection lifecycle

The Agent now opens Core's protocol-2 bidirectional Edge connection. Fresh
installations enroll; persisted identities reconnect with the unchanged
`LE_I64(timestamp) || nonce` Ed25519 challenge signature. Accepted UUIDs, resource
type, target and Swarm node are validated before atomic persistence. Build Pool
identity retains a nil Platform ID and its separate resource ID.

Keys and identity files retain the existing raw-key/PascalCase JSON formats and
SHA256 fingerprints, with private permissions, atomic writes and secure random
key generation. Concurrent initial key creation selects one durable key. Corrupt
files fail closed and remain untouched. Missing keys never silently replace an
enrolled identity. Persistence/reset failures stop the host rather than repeatedly
enrolling with incomplete durable state. Ordinary token fingerprint changes reset enrollment state;
Swarm bootstrap rotation does not. Explicit identity rejection resets only when
an applicable enrollment credential exists; transport failures preserve identity.

Outbound HTTPS keeps native trust and hostname checks, adding configured Core CA
certificates. HTTP warns. The connection uses 16 MiB messages, a bounded outgoing
queue, 30-second heartbeats/keepalive, a 10-second keepalive timeout and exponential
reconnect delay from 1 to 60 seconds with jitter. Docker is probed afresh for
heartbeats; a failed probe reports unreachable with the bound daemon identity.
Injected Swarm identity must match Docker, including worker nodes without a local
cluster document. Cancellation drops the connection, heartbeat probe and queues.

Core's intake previously emitted SessionRejected for database failures. It now
returns retryable Unavailable so enrolled Agents do not discard credentials during
a storage outage. The real-intake PostgreSQL test covers this regression together
with enrollment, signed reconnect, process restart without a token, Build Pool
identity and revocation. The database fixture is disposable; production resources
are not used. Unit/transport tests cover persistence, concurrent creation,
corruption, token/rejection rules, Swarm fields, TLS trust/hostname rejection,
heartbeat reachability, reconnect and shutdown.

Validation results: 52 Agent unit/transport/configuration/lifecycle tests and the
opt-in Core intake test pass. Shared regressions pass: 151 adapter unit tests,
29 Docker transport tests, 12 Edge session tests, five database-backed Edge
transport tests, six contract tests and 10 Core architecture checks. One unrelated
adapter fixture test remains ignored; the Direct live-Docker test was not rerun
in this phase. Strict Clippy for all Agent/adapter targets, formatting, whitespace
and source ownership checks pass. The disposable PostgreSQL container was removed.

Phase 4 implements connection lifecycle only. Commands return an explicit
`unimplemented` failure until Phase 5 supplies dispatch; capability metadata retains
the established profile contract, not a production-readiness assertion.

## Phase 5: Edge command dispatch

All 68 nonzero command kinds now dispatch through the protobuf operations already
used by Direct RPCs. The central match has no wildcard; enum additions require an
explicit handler. A test parses every protocol enum member and proves it reaches
its request decoder before Docker, independently of the capability advertisement.
Unspecified/unknown kinds, wrong schemas and mismatched resource targets are
rejected. Platform and Build Pool targets share the dispatcher.

Interactive exec accepts the command Open payload followed by bounded StreamInput
messages for stdin/resize; both transports share its implementation. Binary exec
preserves byte values, stdout/stderr identifiers and the final exit code. Unary
results and stream items each emit CommandOutput; success or failure then emits
exactly one terminal envelope. A nonzero exec exit remains part of the operation's
payload, separate from transport completion.

A session owns a FuturesUnordered set and command-ID map, capped at 16 commands.
Each command has cancellation and an optional deadline; cancellation drops its
operation/streams before publishing failure. Session loss drops every command,
including pending input and subprocess cleanup guards. Duplicate active IDs close
the session without replacing the original operation. Input overflow or malformed
input cancels only its command. Input queues hold at most 256 messages, output
holds 512 envelopes, and shared 32 MiB byte budgets bound queued input and output.
The wire envelope limit remains 16 MiB. Output stalls are bounded and fail the
connection when delivery is no longer possible.

Swarm-node execution remains denied in this phase. It never inherits the ordinary
unrestricted dispatcher; its allowlist and helper validation are Phase 6.

Validation covers all 68 decoders, unary success/failure, map preservation,
concurrency/byte limits, duplicate IDs, target/schema rejection, deadlines, input
overflow, cancellation and session-drop cleanup. Fake Docker exec connections
verify interactive stdin/resize and binary stdout/stderr bytes plus exit codes.
The actual Core intake integration verifies Platform and Build Pool command
results, failure delivery, live events and cancel/shutdown cleanup against a
disposable PostgreSQL database. The Direct live-Docker regression also passes
after sharing its exec implementation. All disposable database/Docker fixtures
were removed. All 58 Agent tests and six contract tests pass, along with both
opt-in integration tests. Strict Agent Clippy (all targets), formatting, whitespace
and source ownership checks pass.

## Phase 6: Swarm-node restrictions and volume-helper integration

Swarm-node commands now require the configured node identity and an explicit
allowlist. The dispatcher rejects prohibited operations before contacting Docker.
Volume-browser and backup helpers require platform ownership and constrained
mounts, privileges, capabilities, entrypoints and commands. Backup helpers also
enforce resource and lifetime bounds. Binary exec validates the requested operation
and inspected container configuration, then executes by immutable container ID.
Restore volumes require platform/run ownership, a local driver without options,
and no container references before deletion; forced deletion is prohibited.

The existing Rust volume helper is packaged at
`/usr/local/bin/citadel-volume-helper`, with the compatibility alias
`/app/Citadel.Agent.VolumeHelper`. `rust/Dockerfile.agent` provides the
`agent-runtime-base` helper fixture and the default `agent` release target.
`rust/Dockerfile` builds Core independently.

Regression coverage checks every command against the reviewed allowlist, rejects
unsafe helper requests and mismatched node identities, and verifies inspected
state rather than trusting labels alone. The live Docker test built the helper
fixture image and exercised listing, binary download, symlink rejection, protection
of a mounted restore volume, owned restore-volume creation/deletion and cleanup
through the restricted dispatcher. It uses a configured node fixture, without
initializing a Swarm cluster. Full Agent release-image validation and live Swarm
interoperability remain separate gates.

Validation passed: 64 Agent tests, six contract tests, four volume-helper tests,
and the opt-in live helper test. Strict Agent/helper Clippy across all targets,
formatting, whitespace and source ownership checks also pass. Disposable helper
containers, volumes and the test image tag were removed.

## Phase 7: Agent packaging and release integration

The default target in `rust/Dockerfile.agent` uses an Alpine runtime with the same
isolated glibc libraries as Core. It contains
the Agent, Rust volume helper and compatibility alias, Docker CLI/Buildx/Compose,
Git/SSH, CA certificates, Bash and Restic. Restic supports the existing backup
helper commands; Core-only Deno, database client and notification tools are absent.
`rust/Dockerfile` contains only Core build/runtime stages and its required helper.

Core and Agent use the same `build/version.rs` and release build arguments, with
`version.json` as the fallback. Agent Direct info and Edge enrollment/heartbeats
report the compile-time display version. `--version` prints informational metadata.
The new `healthcheck` command probes loopback with a two-second timeout and no
proxy/redirects. Direct TLS trusts the installed certificate chain while allowing
its public hostname; Edge probes HTTP. This measures process liveness independently
of Core/Docker connectivity.

The independent `.github/workflows/agent.yml` pipeline handles relevant pull
requests, main-branch pushes, release tags and manual runs. Native amd64/arm64 jobs
validate the Agent, contracts and volume helper, build release binaries from an
isolated context containing only `rust/` and `version.json`, then smoke-test the
resulting image. Publication
promotes those tested architecture images, verifies the combined manifests/aliases
and signs the digests. Repository/version ancestry checks and existing registry
credentials apply. The stable image names are `ghcr.io/<owner>/citadel.agent` and
`docker.io/<namespace>/citadel-agent`, with version, major.minor and major aliases.

Publication is gated by `CITADEL_RUST_AGENT_RELEASE_ENABLED=true`, intentionally
unset until Phase 8 retires the competing publisher and passes compatibility gates.
No images have been published, no install defaults have been switched, and the
external Agent repository remains untouched. Native arm64 CI and registry promotion
must still execute in GitHub; local validation does not certify either.

Local validation passed: 65 Agent tests, six contract tests, four volume-helper
tests and the live helper integration test. The amd64 release image smoke test
checks release metadata, Direct HTTP/TLS and all Edge profile listeners, custom
ports, health and graceful shutdown, a real scratch-image build, Compose, both
helper paths and Restic backup/restore. The TLS fixture uses a server certificate
with a public hostname, exercising the loopback probe's certificate trust.
Workspace Clippy across all targets passes with warnings denied; formatting,
source ownership, ShellCheck and actionlint pass. Two existing test modules in
Registries/Backups were moved after their implementations to satisfy that lint
gate, without behavior changes.
An isolated build containing only Rust sources and `version.json` produced the

containers, volumes and image tags were removed after validation.

## Phase 8: live compatibility gates (in progress)

Core `AgentClient`/`EdgeIntake` connections, a disposable PostgreSQL database,
authenticated registry and two Docker-in-Docker daemons. No host Docker socket is
mounted into these fixtures and no ports are published. Cleanup removes only the
fixture containers, volumes and network. The native amd64/arm64 image workflow
now requires this test before its publication steps.

The test covers Direct, ordinary Edge and Edge Build Pool image builds, BuildKit
secrets, rejected registry credentials, authenticated push/pull, Compose and Swarm
apply, running Swarm replicas, node inspection, secret creation/deletion, bounded
build timeout, cancellation and temporary credential cleanup. Edge profiles restart
without enrollment tokens and retain their agent identity/key. A completed command
is required before restarting: Core registers a session before Agent persists its
acceptance, so session registration alone is not an acknowledgment of durability.

The Swarm-node fixture obtains a real worker/task identity from a manager and seeds
the corresponding Core projections. It checks rejection of an incorrect task,
successful enrollment, reconnect without the bootstrap file and rejection of build
commands. The executable runs against the worker daemon from the test runner;
this does not exercise Core's service installation workflow itself.

The repository-wide `build/` ignore rule also hid `rust/build/version.rs`; a narrow
exception now includes the shared build script in Git/CI checkouts.

`scripts/test-agent-acceptance.sh CORE_IMAGE AGENT_IMAGE` adds a complete-image
HTTP acceptance gate. It initializes Core, rejects an incorrectly signed Direct
Agent, registers Direct and ordinary Edge platforms, and exercises networks,
volumes, Compose stack apply/start/stop/delete and persisted container inventory.
It also checks offline operation errors, reconnect, Edge identity reuse without

The new gate caught a Direct registration defect: the registration router only
accepted the base transport's address, even though persisted-platform routing
already selected each platform's address. Registration now creates a client for
the submitted address using the same signing identity, TLS policy and CA trust.
The stop scenario also exposed an equal-deadline race: Core's ten-second transport
budget expired at the Agent's ten-second Docker stop grace period. Direct stop
and restart RPCs now include their per-container shutdown grace in addition to
the configured transport budget. Cancellation still interrupts the operation;
a delayed gRPC fixture covers both actions and cancellation.
Edge stack creation also found inconsistent persisted platform names: pending
Edge registration wrote `DockerStandalone`, but Stack validation only recognized
`Docker`. New registrations use the canonical type, and Stack validation uses the
shared classifier so existing standalone records remain usable. Stack persistence
coverage now exercises the previously stored spelling.
Repeated runs also exposed a claim-ownership race: events and inventory could
clear active Stack stop/deletion claims before their RPCs completed, producing
false "operation was superseded" conflicts or deletion 404s. Reconciliation now
preserves owned operations while still recovering ownerless stale Processing
state. Database regressions cover both cases and deliver a container exit event
before completing a state claim, checking for one completion activity.
The native image workflow builds Core as a test fixture and runs the HTTP suite
before publication.
