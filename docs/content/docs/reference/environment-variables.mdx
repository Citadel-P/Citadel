Citadel runtime settings use `CITADEL_` followed by uppercase words separated
by single underscores. Standard tool settings such as `RUST_LOG`, `DOCKER_HOST`
and `PG_*` retain their names. The `.env` downloaded in the [installation guide](/docs/getting-started/install)
contains the settings needed to start Citadel. Add optional settings from this
reference as needed. The defaults are for local HTTP; configure TLS before
sharing an installation.

The sections below cover **Core and its Compose deployment**, followed by
[Direct Agent](#direct-agent-settings) and [Edge Agent](#edge-agent-settings)
configuration. Set each variable on the process or container it belongs to;
Core's `.env` does not configure remote Agents.

`CITADEL_IMAGE`, `COMPOSE_PROJECT_NAME`, and host port settings control Compose.
The application settings must reach the Core container; the supplied Compose
file reads `.env` for this purpose. Recreate Core after editing it:

```bash
docker compose up -d server
```

Keep the installation's project and overlay options on that command. A container
restart alone does not load a changed Compose environment.

## Database and persistent paths

Core chooses its database connection in this order:

1. `CITADEL_DATABASE_URL`, if set: a PostgreSQL URI (`postgres://` or `postgresql://`). A blank or malformed selected URI fails startup.
2. Otherwise, `PG_HOST`, `PG_PORT`, `PG_USER`, `PG_PASSWORD`, and `PG_DATABASE`; credentials are escaped when constructing the URI.

Remove unused overrides instead of leaving them blank. The supplied Compose
PostgreSQL service still requires its `PG_*` credentials. Changing the initial
database password in `.env` does not reset the password of an existing database.

| Setting | Default | Purpose |
| --- | --- | --- |
| `PG_PORT` | `5432` | PostgreSQL port used with the `PG_*` connection settings |
| `CITADEL_DATA_ROOT` | `/app/data` | Persistent Core data and generated recovery keys; match the container's data mount |
| `CITADEL_HOST_ROOT` | `/host` | Read-only host mount used for Docker storage filesystem metrics |
| `CITADEL_PG_DUMP_PATH` | `pg_dump` | PostgreSQL dump executable for control-plane backups |
| `CITADEL_PG_RESTORE_PATH` | `pg_restore` | PostgreSQL restore executable used by offline `restore-system` |

Preserve original keys and verify the database target before
[control-plane recovery](/docs/operations/control-plane-recovery). A new Compose
project does not isolate an external database configured by an override.

## Concurrency limits

Core prepares and tracks work; the execution host admits the expensive operation.
Scripts run on Core or an Agent according to their Run on setting.

| Setting | Default | What it limits |
| --- | --- | --- |
| `CITADEL_BUILDS_PREPARATION_SLOTS` | `2` | Git preparation and outbound build contexts on Core; accepts 1–16 |
| `CITADEL_BUILDS_TRACKING_SLOTS` | `16` | Active build controllers, including retained completion results; accepts 1–128 |
| `CITADEL_BACKUPS_TRACKING_SLOTS` | `16` | Active backup, restore and repository operation controllers combined; accepts 1–128 |
| `CITADEL_SCRIPTS_MAX_PARALLEL_RUNS` | `4` | Core Deno runs, including manual runs and tests; accepts 1–64 |
| `CITADEL_AGENT_BUILD_SLOTS` | `2` | Complete builds on an Agent, including registry pushes and cleanup; accepts 1–64 |
| `CITADEL_AGENT_DATA_SLOTS` | `2` | Backup items, restores and repository maintenance on an Agent; accepts 1–64 |
| `CITADEL_AGENT_HEAVY_SLOTS` | `2` | Builds, data operations and scripts combined on an Agent; accepts 1–64 |

A small installation can keep these defaults. Three independent Agents with two
build slots and two heavy-work slots each can execute six builds while Core
prepares at most two contexts. Set a pool's **Maximum concurrent builds** high
enough for the intended workload; the effective limit is the smallest of the
pool policy, Agent build capacity and Agent shared heavy-work capacity.
Aliases of one Docker daemon share its capacity.

Tracking slots do not launch extra Docker work when a host is full. A multi-volume
backup processes its items sequentially and reserves the host for each item.
Repository, source and restore-destination locks remain held for the protected
operation. These locks renew during execution; expiry alone never permits a
second operation to use storage whose cleanup is uncertain. A source-contention
retry retains the resolved source plan.

Core-local builds, backup helpers and system-backup staging share two local
heavy-work slots. Edge contexts have a separate 32 MiB transfer budget, charged
for raw and encoded payloads; output has its own 32 MiB budget. Control commands
retain independent headroom. These are bounded implementation limits, not extra
configuration knobs.

More slots do not make one job faster or provide CPU/memory isolation. Increase
capacity only when the executing hosts have spare resources. Lowering a pool
policy prevents new over-limit admission while accepted work drains. Agent
capacities are startup settings: let active work finish before recreating an
Agent to change them.

Builds wait when a host is offline or busy. A known pre-execution refusal retries
with a 5–15 second backoff, preserving a commit once resolved. All queued builds,
including those waiting for pool capacity, expire after 24 hours. Ambiguous
execution is never automatically replayed. All script runs, including manual
runs and tests, queue when their selected execution hosts are full or offline. Closing a progress sheet
does not cancel its run.

After changing Core variables, recreate Core with `docker compose up -d server`,
retaining the project's overlay options. Set Agent capacities on each Agent and
recreate it to apply them. The old lifecycle-wide build/backup worker variables
are no longer read.

Core also
persists remote build reservations per Docker daemon, so aliases do not multiply
capacity. Failed or interrupted execution retains its reservation unless the
same Agent confirms cleanup. Core stores that evidence before releasing capacity
with the final run result; restarting an Agent is not cleanup evidence. Core also
rechecks terminal reservations in batches of 16, with five-second Agent checks
and 30 seconds between batches. Confirmed cleanup releases capacity without
retrying the build or changing its outcome. Unreachable Agents, changed Agent
identities and uncertain execution remain held. Administrators can resolve terminal
holds from the build run sheet after verifying cleanup and restarting the original
Agent on the same Docker daemon. Their acknowledgment is audited without retrying
the build. These reconciliation bounds are not additional `.env` settings.

## HTTP listeners and runtime limits

Host-published ports above are separate from the container listeners. The supplied
Compose packages use the listen-port settings for container port targets and the
health check reads the same HTTP port. Bare binaries have no static-root default;
the packaged image sets `CITADEL_STATIC_ROOT=/app/wwwroot` and accepts an override.

| Setting | Default / units |
| --- | --- |
| `CITADEL_HTTP_LISTEN_PORT` / `CITADEL_EDGE_GRPC_LISTEN_PORT` | `8000` / `8001` |
| `CITADEL_HTTP_CORS_ORIGIN_<n>` | No origins; indexed list ordered numerically, sparse indices allowed; blank entries rejected |
| `CITADEL_HTTP_FORWARDED_LIMIT` | `1` trusted hop |
| `CITADEL_HTTP_BODY_LIMIT_BYTES` | `2097152` bytes |
| `CITADEL_HTTP_REQUESTS_PER_MINUTE` | `600` |
| `CITADEL_DATABASE_MAX_CONNECTIONS` | `5` |
| `CITADEL_DOCKER_SOCKET` | `/var/run/docker.sock` inside Core |
| `CITADEL_DOCKER_TIMEOUT_SECONDS` | `10` seconds |
| `CITADEL_STATIC_ROOT` | Optional frontend directory |
| `CITADEL_SHUTDOWN_TIMEOUT_SECONDS` | `10` seconds |
| `CITADEL_LOG_COLOR_ENABLED` | Terminal detection; JSON always omits ANSI color |
| `CITADEL_STATS_BATCH_SIZE` | `500` |
| `CITADEL_EVENT_QUEUE_CAPACITY` | `256` |
| `CITADEL_SWARM_RECONCILIATION_INTERVAL_SECONDS` | `1800` seconds |
| `CITADEL_RETENTION_INTERVAL_SECONDS` | `900` seconds |
| `CITADEL_REALTIME_ENABLED` | `true`; disabled realtime skips its other settings |
| `CITADEL_REALTIME_QUEUE_CAPACITY` / `CITADEL_REALTIME_MAX_CONNECTIONS` | `64` / `8` |
| `CITADEL_REALTIME_SUBSCRIBE_TIMEOUT_SECONDS` / `CITADEL_REALTIME_SEND_TIMEOUT_SECONDS` | `5` / `2` seconds |
| `CITADEL_REALTIME_AUTH_RECHECK_SECONDS` | `30` seconds |
| `CITADEL_REALTIME_SNAPSHOT_LIMIT` | `1024` |

In the development overlay, `CITADEL_DEV_DOCKER_SOCKET` selects the host socket
mount source; Core and the entrypoint both use `/var/run/docker.sock` inside the
container. The launcher derives this source from its native `CITADEL_DOCKER_SOCKET`.

Set these on the Agent container. The generated setup command supplies its
identity and Core public key; follow the [Direct Agent guide](/docs/operations/agent)

| --- | --- | --- |

| `CITADEL_AGENT_ID` | Required | Platform or dedicated Build Pool UUID from setup; remains stable when the address changes |
| `CITADEL_CORE_PUBLIC_KEY` | Required | Base64 Ed25519 public key emitted by Core setup |
| `CITADEL_AGENT_PORT` | `9000` | Agent listener port inside the container |
| `CITADEL_AGENT_BUILD_SLOTS` | `2` | Complete build attempts on this Agent, including pushes; accepts 1–64 |
| `CITADEL_AGENT_DATA_SLOTS` | `2` | Data operations including helper cleanup; accepts 1–64 |
| `CITADEL_AGENT_HEAVY_SLOTS` | `2` | Shared build/data occupancy; accepts 1–64 |

## Edge Agent settings

Set these on the Edge Agent container. Use the command generated by Citadel;
see the [Edge Agent guide](/docs/operations/edge-agent). Edge mode does not read
the Direct-only identity, Core public-key, or listener TLS settings above.

| Setting | Default / requirement | Purpose |
| --- | --- | --- |
| `CITADEL_AGENT_MODE` | `edge` required | Selects the outbound Edge connection |
| `CITADEL_AGENT_BUILD_SLOTS` | `2` | Shared build capacity across Edge commands and replacement connections; accepts 1–64 |
| `CITADEL_AGENT_DATA_SLOTS` | `2` | Data operations including helper cleanup; accepts 1–64 |
| `CITADEL_AGENT_HEAVY_SLOTS` | `2` | Shared build/data occupancy; accepts 1–64 |
| `CITADEL_CORE_URL` | Required | Core's Edge gRPC origin, not its browser/API endpoint |
| `CITADEL_EDGE_AGENT_PROFILE` | `edge-agent` | `edge-build-agent` selects a dedicated Build Pool Agent; Swarm node profiles are generated by Core |
| `CITADEL_EDGE_ENROLLMENT_TOKEN` | Required for initial enrollment | Enrollment credential from Citadel; an enrolled Agent reconnects using its persisted identity |
| `CITADEL_EDGE_CORE_CA_CERTIFICATE_PATH` | Optional | PEM trust bundle for an HTTPS Core endpoint using a private CA |
| `CITADEL_EDGE_AGENT_KEY_PATH` | `/app/data/edge-agent.key` | Persisted private-key path |
| `CITADEL_EDGE_IDENTITY_PATH` | `/app/data/edge-agent.identity.json` | Persisted enrollment identity path |

Preserve the Agent's data volume. Dedicated Build Pool setup commands can select
profile-specific key and identity paths; keep those generated values. Core also
supplies Swarm node bootstrap and identity variables automatically.

### Script execution capacity

| Variable | Default | Purpose |
| --- | --- | --- |
| `CITADEL_SCRIPTS_MAX_PARALLEL_RUNS` | `4` | Deno processes running locally on Core. |
| `CITADEL_SCRIPTS_MAX_REMOTE_RUNS` | `16` | Remote script runs Core tracks concurrently (1–256); no local Deno process is created for them. |
| `CITADEL_AGENT_SCRIPT_SLOTS` | `4` | Concurrent Deno scripts on each Agent (1–64), also bounded by `CITADEL_AGENT_HEAVY_SLOTS`. |

All triggers enter the durable queue. A busy host defers work; the Core local
limit does not prevent execution on a free Agent. Increase Agent capacity only
when that host has enough memory and CPU for scripts alongside builds and backups.
Remote scripts use Core's public HTTPS origin, not Core's loopback API address.
